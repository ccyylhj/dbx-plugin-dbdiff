# 库差异对比（DB Diff）— DBX 插件

对当前连接 + 库打只读快照，然后把快照和**实时数据库**对比，导出可以拿到另一个环境执行的 SQL。

**支持两个数据库族**，按连接的 `type` 自动选：

| | 认哪些 type | 说明 |
|---|---|---|
| MySQL 族 | `mysql` `mariadb` `doris` `starrocks` | 原始目标 |
| PostgreSQL 族 | `postgres` `kingbase` `gaussdb` `highgo` `vastbase` `uxdb` `yashandb` `greenplum` `redshift` | **按协议族算，不是某一个产品**。金仓（KingbaseES）、GaussDB 这些都走 PG 协议，`dbx connections list` 一律报 `postgres` |

认不出的类型**明确报错**，不猜——拿 MySQL 语法去打 MongoDB 只会得到一个莫名其妙的服务器错误。
所有语法差异集中在 `backend/src/dialect.rs`，别的模块写一遍就够。

### 两族之间实际差在哪

| | MySQL | PostgreSQL |
|---|---|---|
| 标识符引号 | `` `x` `` | `"x"` |
| 当前库 | `DATABASE()` | `current_database()` |
| 结构作用域 | `TABLE_SCHEMA = '库名'` | `table_schema = current_schema()` |
| 表引用 | `` `库`.`表` `` | `"表"`（PG 不能跨库） |
| 条件式 | `IF(c,a,b)` | `CASE WHEN c THEN a ELSE b END` |
| 备份表 | `CREATE TABLE x LIKE y` | `CREATE TABLE x (LIKE y INCLUDING ALL)` |
| 改列类型 | `MODIFY COLUMN` | `ALTER COLUMN ... TYPE` |
| 加索引 | `ALTER TABLE ... ADD KEY` | `CREATE INDEX ... ON ...` |
| 表引擎 | `ENGINE=InnoDB` | 没有这个概念 |
| 索引来源 | `information_schema.STATISTICS` | `pg_index`（标准视图里根本没有索引） |
| 列类型 | `COLUMN_TYPE`（`varchar(64)`） | `udt_name` + 长度/精度拼出来 |
| 库选择器 | 列出所有库 | **只有连接自己那个库**（PG 连接不能跨库） |

数据通道两边几乎一样：`dbx query` 对两族**都把值返回成字符串**，`COUNT(*)`、
`ORDER BY ... LIMIT n OFFSET m`、行构造器 `(a,b) IN ((..),(..))` 全都通用。

### 六张系统表的列清单是**发现**来的，不是写死的

打快照时从 `information_schema` 按序号读该表**当前的全部列**。写死的只有三样，因为它们定义的是语义
而不是形状：**标识列**（`<表>_id`）、**分页排序键**（数据库自己的主键）、**内置条件**
（`ds_active = '1'`）。`tables.rs` 里那份编译进去的列清单降级成"目录读不到时的兜底"。

这不是洁癖，是实测逼出来的：同一份配置下
- `timeuse`（MySQL）的 `dsfa_rm` 有 **41** 列
- `eb169`（KingbaseES）有 **41** 列
- `fnec_prod`（KingbaseES）只有 **36** 列，缺 `pinyin_value`、`py_value`、`ds_security_level_*`

任何一份写死的清单都会在其中某一台上读出不存在的列——那是**报错**，不是空结果。

### 列明细变了怎么办

表加了列，快照是加列之前打的——这时候**不拒绝对比**：

| 情况 | 处理 |
|---|---|
| 列清单一致 | 一次 hash，和以前完全一样 |
| 本库**多了**列 | 对比按**基准快照的列**算 hash（这些列都还在，两边含义才一致）；**新快照记本库当前的列**，下一趟就对齐了；报告里单开一节说明 |
| 本库**少了**列 | **拒绝对比**。基准快照的 hash 覆盖了一个已经不存在的值，重算不出来；硬比会把每一行都报成"修改" |
| 标识列变了 | **拒绝对比**。那重新定义了"一行是什么"，没什么可调和的 |

**多了列的时候，逐行这么判：**

| 这一行 | 处理 |
|---|---|
| 旧列 hash 不一样 | 正常走修改（备份 + 删 + 插），INSERT 带着新列 |
| 旧列 hash 一样、新列**全是空**（NULL 或空串） | **不动**。表加了一列但每行都是空的，为这个写整张表没有意义 |
| 旧列 hash 一样、新列**有一个有值** | 也走修改，把新列的值推过去。hash 看不到它（那些列本来就在 hash 之外），但目标库没有这个值，不推过去就是漏了 |

「空」= NULL 或长度 0 的字符串。`NOT NULL` 的列存不了 NULL，所以那边"没有值"就长成 `''`。

只在"多了列"那一趟才算两次 hash（一次按快照的列给对比用，一次按本库的列给新快照用）。
**一致时仍然只算一次**——这是常态，不能变慢。

**03/04 的列清单取的是新快照（本库当前），不是基准快照。** 值是按本库形状取的，列清单要是按基准的来，
`zip` 会把新列的值**静默丢掉**；列顺序一旦不同还会整体错位。这个 bug 是写实验室抓出来的——
只读的验收测试看不见它。

新快照必须自洽：它 `meta.json` 里的 `columns` 声明的是"这些 hash 覆盖了哪些列"。
如果漂移时图省事、把按旧列算的 hash 塞进一个记录新列的快照，**下一趟对比会把整张表的每一行
都报成修改**。验收里有一条专门盯这个：漂移那一趟写出的快照，立刻拿它自己比一次，必须是 0 差异。

- **数据通道**：固定的六张系统表，按 `<表>_id` 对齐、比整行 hash
- **结构通道**：全库表结构（可用正则过滤表名）
- **快照的标识是 `连接 + 库`**：同一个连接下两个库的历史互不相干，界面和存储都按这个二元组分开
- 插件**全程只读**：不写任何数据库，也从不连接目标环境

```
manifest.json          工作台贡献 + 后端入口
ui/index.html          沙箱界面
backend/src/
  tables.rs            六张表的表名、列、标识、排序键（从库里生成，不是手抄）
  snapshot.rs          分页采集、行编码、过滤条件拼接、后台任务状态
  schema.rs            information_schema 采集、结构对比、DDL 生成
  diff.rs              两条通道的对比 + SQL 写出
  cli.rs  config.rs  encode.rs  store.rs
build.py               编译 + 打包 .dbxp
acceptance-test.py     端到端验收
PLAN.md                设计与取舍
```

## 构建与安装

```bash
python build.py                      # 给本机打包
python build.py -t darwin-arm64      # 在 Mac 上打 Mac 的包
python build.py --list-targets       # 有哪些 target
```

**一个平台一个包，mac 和 windows 不能共用一个。**

包里的 sidecar 是按某一个 target 编的，manifest 里的 `entrypoints.backend.executable`
指向那个 target 的二进制（`bin/<target>/...`）——DBX 的包布局就是这么定的，
运行时会按 manifest 里写的路径去解析，没有平台映射表。所以
`...-windows-x64.dbxp` 和 `...-darwin-arm64.dbxp` 是同一份源码的两个产物。

带原生 sidecar 的插件**不能用 `universal`**——那是给纯前端插件准备的。
默认矩阵是 `darwin-arm64`、`darwin-x64`、`windows-x64`、`linux-x64`、`linux-arm64`。

构建完的路径：`dist/dbx.demo.dbdiff-<版本>-<target>.dbxp`。

### Mac 上怎么出包

**必须在 Mac 上编**，交叉编译不行：sidecar 要链接平台自己的 libc，而从 Windows 编 macOS
目标需要 macOS SDK，Apple 的授权把 SDK 限定在 Apple 硬件上使用。所以 Mac 包由 CI 出——
`.github/workflows/build.yml`，三个 job 各自跑在自己那个平台的 runner 上
（`windows-2022`、`macos-15`、`macos-15-intel`），每个 runner 只编自己那个 target。

推一个 `v*` 标签就会构建并把三个包挂到 Release 上：

```bash
git tag v0.1.1 && git push origin v0.1.1
```

不想打标签也可以在 Actions 页面手动跑一次（只有 artifacts，没有 Release）。
本机想验一遍的话，在 Mac 上直接 `python build.py -t darwin-arm64` 就行。

**状态**：三个平台都能编过、链接上、打出包。**但那个 Mac 包没有在真机上装过、跑过。**

### 安装

插件中心 → 第三方与开发者选项 → 打开「允许安装未签名开发包」→ 安装对应平台的 .dbxp →
工作台 → 打开。

装错平台的包**安装时不会被拒**（宿主只检查 manifest 指的那个文件在不在，包里是有的），
但启动 sidecar 时会失败——Mach-O 内核不执行 PE 文件。

### dbx CLI 在哪

插件读库全靠 `dbx query` 子进程，所以第一步是找到 `dbx` 这个 CLI
（`npm install -g @dbx-app/cli` 装的那个）。Windows 上它就在
`%APPDATA%/npm/node_modules` 里，找到就完了；macOS 上麻烦得多，两个原因：

1. Node 多半是版本管理器装的（nvm / fnm / volta / asdf），全局前缀在
   `~/.nvm/versions/node/<版本>/lib/node_modules` 这类要列目录才知道的地方
2. **从 GUI 启动的进程不继承终端的 PATH**——终端里 `dbx` 好好的，插件里找不到

所以 `cli::resolve` 会依次试：`DBX_CLI_BIN` → 配置里的 `cliPath` → 那串 npm 前缀 →
PATH 上的真程序 → PATH 上的 npm shim（它是 `bin/dbx.js` 的软链，不能直接跑，
但顺着它就能推出包在哪）→ **问一次登录 shell** `command -v dbx`。

都落空时报错会把**查过的每一个位置**列出来。真找不到就在面板上把 `dbx` 的完整路径
填进「dbx CLI 路径」，它会替代自动查找。`testenv.py` 是同一套顺序的 Python 版，
两个测试脚本用的就是插件会用的那个 CLI。

## 连接与库

顶栏是**连接**和**库**两个下拉，挨着放。

- 选完连接会自动拉该连接的库列表（`information_schema.SCHEMATA`，去掉 MySQL 自己的
  `information_schema` / `performance_schema` / `mysql` / `sys` 四个）
- 库的默认值取**连接自己配置的那个库**（`dbx connections list --json` 里的 `database` 字段），
  不用再查一次
- **连接没配默认库**（MySQL 连接可以不带库）时留空，显示「请选择数据库」，由你选
- 连接配了库但那个库不在列表里（没 SHOW 权限、或库被删了）时**仍然作为选项保留**——
  它是连接的指向，藏起来就等于偷偷换了目标

**没选库时点「新建快照」或「对比」会弹框提示**，不会用别的库凑合。按钮本身不置灰：
点一下告诉你缺什么，比一个不说话的灰按钮有用。

连接没有默认库时，状态栏会显示「这个连接没有默认数据库 —— 选一个库再开始」。**它跟着条件走**：
选了库就消失，换到另一个也没默认库的连接又会出现。这条提示是按文本记住的，所以清除它
永远不会顺手抹掉期间冒出来的真实报错。

「新建快照」下面的状态栏右边有个**清除**按钮——任务跑完留下的报错和提示可以用它清掉。
任务进行中它是灰的：那时候状态栏是进度读数，抹掉会让人以为卡住了。

库名存进快照的 `meta.json`，快照目录也按它分层：

```
<数据目录>/snapshots/<连接>/<库>/<时间戳>/
```

所以两个库的快照在界面上和磁盘上都不会混在一起。**对比用的是界面上选的库**；如果传进来的
基准快照记录的库不是当前选的那个，直接报错让你刷新，不给确认的机会——「拿 A 库的快照比 B 库」
不是一个有安全答案的问题。

旧的扁平目录（`<连接>/<时间戳>/`）在第一次列出快照时会**自动搬进对应的库目录**，
用的是快照自己 `meta.json` 里记的库名。搬运是同卷 `rename`，原子操作，中途崩了最多是留在原地。

## 界面

左边是六张表，**每张表的过滤条件输入框在表名下面单独一行**。再下面是表结构过滤正则（匹配表名）。
输入的值存到插件数据目录的 `config.json`，下次打开自动回显。

点「新建快照」采集。快照列表每条的第一个字段是**采集时间**（快照 id 本身就是时间戳，再显示一遍是重复的，
现在只在 tooltip 和详情弹窗里出现），第二个字段是行数和表结构数量。每行三个按钮：

- **对比** —— 和当前实时数据比，报告直接显示在右边（比的是同一个连接 + 库）
- **详情** —— 弹窗看这条快照记录的：每张表的行数 / 页数 / sha256 / 折叠数 / 过滤条件
- **删除**

对比结果的右上角有「打开 SQL 生成位置」和「复制路径」。

报告里的数字是有颜色的：数据差异表的**新增标绿、修改标黄、删除标红**（值为 0 的不上色）；
折叠警告那一段标题和条目带 ⚠ 且标题标红。

**对比的同时会把当前状态也存成一份快照**，所以对比完快照列表里会多一条。代价是零——同一批行既喂给对比也写进新快照。

## 运行中与取消

点「新建快照」或「对比」后，**除「取消」外的所有按钮和输入框都会被禁用**——包括连接下拉、刷新、
每张快照的对比/详情/删除、过滤条件输入框。任务结束后按各自的正常状态恢复（哪个该灰就还是灰的）。

「取消」会**杀掉正在运行的那个 `dbx` 进程**，不是只设个标志等它自己返回。差别很大：一页数据在慢链路上
可能要跑几分钟，只设标志的话点完取消会一直卡到那条查询返回为止。同时按钮会变成「取消中…」并给出提示，
避免看起来像没反应。

## 过滤条件

输入框里**只写条件本身**，不要写 `where` / `and` / `or`：

```
id not like 'test%'                         ✓
and id not like 'test%'                     ✗（会被自动剥掉开头的 and，但别写）
ds_active = 1 AND name like 'x%'            ✓
```

拼进 SQL 时是这样：

```sql
WHERE ds_active = '1' AND (id not like 'test%')
```

两件事是自动的：

- **开头的 `and` / `or` / `where` 会被剥掉**（写错了不会拼出 `AND and ...`）
- **你的条件会被括号包起来**。没有括号的话 `ds_active='1' AND a=1 OR b=2` 会被解析成
  `(ds_active='1' AND a=1) OR b=2`，`OR` 后面就逃出了 `ds_active` 的限定

`ds_active = '1'` 是写死在 `tables.rs` 里的内置条件，不在输入框里，删不掉。

### 对比用的是输入框里的当前值

不是快照里记录的那条。**和快照记录的不一致时会先弹框确认**：

```
当前过滤条件与快照过滤条件不一致，是否继续？

【dsfa_rm】
  快照：ds_active = '1'
  当前：ds_active = '1' AND (id not like 'test%')
```

点「继续」才开任务，点「取消」什么都不发生。确认后：

- 对比按新条件算
- 附带存的新快照记的也是新条件，下次拿它做基准不用再确认
- 报告头部写明"本次对比使用的过滤条件与基准快照不一致（已确认继续）"，并列出改了哪些
- 报告里「每张表的过滤条件」、`00-precheck.sql` 的 `WHERE`、`03` / `04` 里每张表的 `-- 过滤:` 注释，
  写的都是**本次用的那条**，不是快照记的那条。生成的 SQL 里所有的 `WHERE` 和生成它的那次对比
  是同一个条件，这一条是有测试盯着的

## 行标识

**只用 `<表>_id` 一列，不是数据库自己的主键。** 五张表的数据库主键是 `(<id>, ds_version)`，
这里故意不要 `ds_version`，配合内置的 `ds_active = '1'`，语义是「每个 id 保留一条活跃行」。

`dsfa_route_version` 没有 `ds_active` 列，所以只有 id 条件。

分页的 `ORDER BY` 用的**是数据库自己的联合主键** `(id, ds_version)`（从 `information_schema` 按字段序生成）。
它唯一，页边界有定义；它是索引上的两个短列，排序代价小。

### ⚠ `dsfa_rm` 目前有 3 个 id 重复

即使加了 `ds_active = '1'`，`dsfa_rm` 仍有 3 个 id 各对应两行（`ds_version` 一个是 `1`、一个是 `project`，**两行 `ds_active` 都是 1**）。

快照每个标识只能存一条，所以**有 3 行会被丢弃**——按联合主键排第一的那条留下（即 `ds_version='1'`）。插件不会假装没发生：

- `meta.json` 里该表记 `collapsed` 计数和样例 id
- 报告的「标识重复，有行被折叠」一节逐条列出
- 界面对比完成时显示 `⚠ 3 行标识重复被折叠`，快照详情里也能看到
- `00-precheck.sql` 比的是**目标库原始 `COUNT(*)`**（含重复），不受折叠影响

要精确保留哪一条，在该表过滤框里写 `ds_version = 'project'`（或 `= '1'`）。

## 网络抖动

每次 `dbx query` 都开一个**新连接**，一次快照要开十几个。远程库上任何一个握手卡住都会让整个任务失败。

所以**连接级**错误会重试两次（间隔 2s / 4s）：`connection timed out`、`Connection pool checkout timed out`、
`Can't connect to MySQL server`、`Communications link failure`、`Lost connection`、`Connection reset`、
`connection refused`。

最后加的那条（`Connection pool checkout timed out`）是实测撞出来的：一次验收跑在第 5 步倒下了，
报的就是这个——服务端连接池还没轮到握手就超时了，和"连接超时"是不同的报错文本，所以一直没被重试。

SQL 错误**不重试**——它是确定性的，重试只会浪费时间并掩盖真正的报错。

`COUNT(*)` 失败仍然不中断快照（那只是校验用的），但会在报告里单开一节说明：
"这几张表的 expected 用的是写入行数，不是真实行数，目标库有重复标识时这个值会偏小"。

## 分页

每页固定 `LIMIT 10000` + `--limit 10000`，翻到某页不满为止。

`dbx query` 不带 `--limit` 时**最多返回 10000 行且不报错**（`crates/dbx-core/src/db/mysql.rs:4054`，
CLI 的 JSON 输出里没有 `truncated` 字段）。

## 输出的文件

```
<输出目录>/<连接>/<库>/<时间戳>/
  00-precheck.sql      只读。一条 UNION ALL 语句查完六张表，verdict 全 ok 才继续
  01-schema-auto.sql   建表 / 加列 / 加索引 / 类型放宽
  02-schema-review.sql 类型收窄或转换、新增外键。人工逐条判断
  03-data.sql          新增和修改的行：备份 → 删除 → 插入。**一行一条 INSERT**
  04-delete.sql        对比出来是删除的行：备份 → 删除。用自己的备份表
  report.md            摘要（就是界面上显示的那份）
  manifest.json        输入身份 + 各文件 sha256
```

**两个文件处理的 id 集合不相交**——一个 id 要么在被写入、要么在被删除，不会两边都有——所以
**先后顺序无所谓**，按编号跑就是。各自建自己的备份表（`_bak_` / `_delbak_`），单独跑任何一个，
它删掉的东西都能从自己那张备份表里找回来。

**某一类一条语句都没有，那个文件就不生成。** 只改了数据的运行只给三个文件；一次干净的运行
只给 `00-precheck.sql` 和 `report.md`。空文件会让人以为「有东西要评审，只是没写进来」，而且
四个文件里两个是空的，就是多开两个文件。报告里逐条写明哪个文件没有生成；
`manifest.json` 的 `files` 里也只有真正写出来的那些。

### 前置校验是一条语句

`00-precheck.sql` 里只有**一条** `SELECT`，六张表用 `UNION ALL` 串起来，每行一个 `verdict`：

```sql
SELECT 'dsfa_rm' AS table_name, 1237 AS expected, COUNT(*) AS actual,
       IF(COUNT(*) = 1237, 'ok', 'MISMATCH -- 数量不一致') AS verdict
  FROM `dsfa_rm` WHERE ds_active = '1'
UNION ALL
SELECT 'dsfa_route_version' AS table_name, 90 AS expected, COUNT(*) AS actual,
       IF(COUNT(*) = 90, 'ok', 'MISMATCH -- 数量不一致') AS verdict
  FROM `dsfa_route_version`
;
```

- 每行带着**自己的过滤条件**，和本次对比实际用的那条一致
- `expected` 是**目标库原始 `COUNT(*)`**，所以标识折叠不影响它
- 用 `UNION ALL` 不用 `UNION`：`UNION` 会顺手合并完全相同的行，而两张空表的两行恰好就是完全相同的
- 折叠和 `COUNT(*)` 取不到的提示都挪到语句上方了——一条语句里没有"某张表旁边"可以挂注释

### 没有检测语句

`01` / `02` 里**不再有 `SELECT ... information_schema ...` 的检测行**。执行时失败的跳过，
修好后整个文件重跑就行——文件里的语句重复执行是安全的。

代价是中途失败后没法靠检测行判断从哪继续，得自己看失败的那条。换来的是文件短一半。

### 数据变更的形状

按**对比结果**分成两个文件，不是按语句类型分。

`03-data.sql` 管**新增和修改**的行，每张表是完整的「备份 → 删除 → 插入」：

```sql
CREATE TABLE IF NOT EXISTS `dsfa_mm_bak_20260920_094436` LIKE `dsfa_mm`;

INSERT INTO `dsfa_mm_bak_20260920_094436` SELECT * FROM `dsfa_mm`
  WHERE (`dsfa_mm_id`) IN ('abc', 'def', ...);

DELETE FROM `dsfa_mm` WHERE (`dsfa_mm_id`) IN ('abc', 'def', ...);

INSERT INTO `dsfa_mm` (`dsfa_mm_id`, ...) VALUES ('abc', ...);
INSERT INTO `dsfa_mm` (`dsfa_mm_id`, ...) VALUES ('def', ...);
```

- **INSERT 的行都在删除列表里**，不只是真正消失的行。目标库如果已经有一行同 id（源库从来
  没有过的行），不先删掉插入会撞唯一键；先删掉它被备份下来，再被源库的值覆盖
- **一行一条 INSERT**：某一条失败就跳过那一条，其余照跑，不用为了一行回退整个文件。
  多行 `VALUES (...), (...)` 拼一大坨，列一宽也基本没法看
- 要整个重跑就整个文件重跑。03 里的备份-删除-插入是一个整体，拆开跑会撞唯一键

`04-delete.sql` 管**对比结果是删除**的行——快照里有、现在没有了——**只删不写**：

```sql
CREATE TABLE IF NOT EXISTS `dsfa_mm_delbak_20260920_094436` LIKE `dsfa_mm`;

INSERT INTO `dsfa_mm_delbak_20260920_094436` SELECT * FROM `dsfa_mm`
  WHERE (`dsfa_mm_id`) IN ('xyz');

DELETE FROM `dsfa_mm` WHERE (`dsfa_mm_id`) IN ('xyz');
```

**04 建自己的备份表**（`_delbak_` 而不是 `_bak_`），不是复用 03 那张。这样两个文件各管各的，
单独跑任何一个，它删掉的东西都能从自己那张表里找回来。

**两边的 id 集合不相交**：一个 id 要么在被写入、要么在被删除，不会两边都有。所以先跑哪个都行。

备份表名是 **`<表名>_bak_<时间戳>`** / **`<表名>_delbak_<时间戳>`**。原来的
`_dbx_bak_<时间戳>_<表名>` 把时间戳放前面，一次运行的所有备份按名字排在一起，而不是按表名——
但人找备份是按表名找的。

重跑某个文件时，它已经备份过的那几条会因为备份表的主键（`LIKE` 复制过来的）重复而失败，
跳过即可——那说明已经备份过了。

- `CREATE TABLE ... LIKE` 建的是**空表**——只复制结构，不复制数据。备份的数据在下面那条
  `INSERT ... SELECT` 里，而且**只有要删掉的那些标识**，不是全表
- **备份取的是目标环境上的当前行**，不是快照里的值
- **删除和备份用同一份标识列表，这份列表包含新增和修改的 id**。目标库如果已经有一行同 id
  （源库从来没有过的行），不先删掉，插入会撞唯一键；先删掉，它被备份下来，再被源库的值覆盖
- 目标库没有的标识，备份的 `SELECT` 自然查不到东西，不会凭空多出行来
- 标识列表按 500 个一组分块（这个数字的来历见下面「IN 列表能放多少个」）
- 备份表不自动删除
- **修改 = 备份 + 删 + 插**，不做 UPDATE

### IN 列表能放多少个

**MySQL 没有 1000 个元素的硬上限**（那是 Oracle 的规矩）。真正的悬崖是内存：

| 列表长度 | 语句大小 | 结果 |
| ---: | ---: | --- |
| 500 | 18 KB | ok |
| 5,000 | 180 KB | ok |
| 10,000 | 360 KB | ⚠ 警告 3170 |
| 50,000 | 1.8 MB | ⚠ 警告 3170，仍然跑得完 |

8.0.36，32 字符的 id，默认 `range_optimizer_max_mem_size` = 8 MB。到一万个左右 MySQL 就不再用
索引，退回全表扫描，并报：

```
Warning 3170: Memory capacity of 8388608 bytes for 'range_optimizer_max_mem_size' exceeded.
```

**是警告加全表扫描，不是报错**——语句照样出结果，只是慢。实测到 5 万个元素、1.8 MB 的语句都跑得完。

所以 `CHUNK = 500` **不动**：离一万还有二十倍，一条语句才 18 KB。要改这个常量的话，
预算在这儿——按内存算大约一万个元素封顶，id 更长就按比例往下调。

## 几条不变量

1. **`diff(快照, 实时读)`** —— 永远和实时读比，绝不拿两份历史快照互比。这是自愈性的唯一来源。
2. **数据 hash 只覆盖参与对比的那些列，不含类型。** 所以某列改了类型不会让全表每一行都算
   「修改」——类型是结构通道的事。
3. **结构对象只增不删。** 表 / 列 / 索引 / 外键的删除只进报告，永不生成 `DROP`。
   （数据行的删除是生成的——那是「备份 + 删 + 插」这套形状的一部分，和结构是两回事。）
4. **列清单是发现来的，不是编译进去的**（见上）。写死的只有标识列、排序键、内置条件——
   那些定义的是语义，不能跟着数据漂。
5. **列明细漂移按快照的列比、按当前列存。** 快照记录的 `columns` 和它文件里的 hash 必须永远
   描述同一件事——这是这个插件最容易悄悄出错的地方。
6. **标识列变了、或本库少了基准快照 hash 过的列，就拒绝对比**，要求重新打快照——
   那两种情况下算不出可比的 hash，硬算会把每一行都报成「修改」。
7. **类型放宽自动执行，其余类型变更人工判断。** 判断标准只回答一个问题：**会不会丢数据**。
   会、或者拿不准，就进 02——进 02 的代价是有人看一眼，进 01 的代价是静默截断一列生产数据。
8. **快照属于「连接 + 库」**，两者都是路径的一部分。想比另一个库就换库重打，不要指望拿 A 库的
   快照去比 B 库——那生成的 SQL 会去改错误的数据。
9. **报告和生成文件里的过滤条件，永远是「本次用的那条」**，不是快照记的那条。
   生成的 SQL 里所有的 `WHERE` 和产生它的那次对比必须是同一个条件。

## 界面上的一个坑

插件界面跑在 `sandbox="allow-scripts"` 的 iframe 里（`PluginWorkbenchHost.vue:258`），
**没有 `allow-modals`**。这意味着 `window.confirm()` / `alert()` 不会显示，直接返回 `false`。

所以界面里所有确认都是自绘的页内弹窗（`confirmDialog`），包括对比前的条件不一致提示和删除快照。
新增弹窗时不要用原生的。

## 已知边界

- 只支持 MySQL 方言（`information_schema`、反引号、行构造器 `IN`）
- 六张表的列、标识、排序键写死在 `tables.rs`，由脚本从 `information_schema` 生成
- 列注释 / 表注释、`AUTO_INCREMENT`、分区、视图、触发器、存储过程一律不比
- 结构正则用 `fancy-regex`（`regex` 不支持 `(?!...)`）
- 类型收窄 / 转换单独成文件：`varchar(1000) -> varchar(100)` 会静默截断数据
- MySQL 的 DDL 隐式提交，几个文件不是一个事务，中途失败会留下半截状态

### 写实验室（`drift-lab.py`）

验收测试的契约是**绝不执行任何 SQL**，这条得守住。但有三件事只有写才能验：

1. **真的列漂移**。验收里是靠改基准快照的记录模拟的，模拟不出"旧列 hash 相同、新列有值"这个
   真正的判定场景
2. **生成的 SQL 到底能不能跑**。这个项目里没有别的东西执行过它
3. **`ADD COLUMN ... NOT NULL` 的真实行为**——两个方言在这里是有记录的差异的

所以单独一个脚本，**明确会写**：加列、填值、删列，还会把生成的语句执行一遍。

```bash
python drift-lab.py 127.0.0.1 test_a    # 默认值就是这两个
```

它**拒绝**对不以 `test_` 开头的库运行（要强行跑得显式 `--force`）。清理只按本轮**确切生成**的备份表名，
不用 `LIKE` 模式——SQL 里 `_` 是单字符通配符，`'%_bak_%'` 会连别人的备份表一起匹配上。

跑完把库恢复原状（探针列删掉、这轮建的备份表删掉）。

端到端覆盖：拿自己的快照比自己必须是 **0 差异**，而且这时除了 `00-precheck.sql` 和 `report.md`
**一个 sql 文件都不生成**；通过**改基准快照文件**注入差异，逐类验证方向和落点（这和真实变更的形状
一样：基准里没有的就是新增，只在基准里的就是被删的）；**同一次注入里一列放宽、一列收窄**，
验证前者落 01、后者落 02；**03 是备份-删除-插入、一行一条 INSERT**（删除列表包含新增的 id），
**04 只删不写、且用自己那张备份表**；两边的 id 集合验证为不相交（删掉的那个 id 不出现在 03，
新增和修改的那两个不出现在 04）；
过滤条件变化时**不启动任务**而是返回待确认，且报告里「每张表的过滤条件」写的是**本次用的那条**；
库是必填参数、快照落在「连接 + 库」两级目录下、点名的库在 `databases/list` 里。
**不执行任何 SQL。**

库名是从连接的 `database` 字段取的，所以这个测试只能对**配了默认库**的连接跑；没配的那些会被跳过。

**同一套检查两族都跑**：脚本从连接的 `type` 认出方言，引号、`CREATE TABLE ... LIKE`、
`MODIFY COLUMN`、有没有 `ENGINE` 这些期望值跟着变。所以两条命令都必须是
`ALL CHECKS PASSED`，改动才算数。

`00-precheck.sql` 的形状有单元测试兜着（`diff::tests`），会把生成的那条语句打出来——它抓到过一个双重反引号——表名被包了两层反引号，那种 SQL 在目标库上会直接语法错误。
端到端测试跑不到这个，因为它只读文件、不执行。

界面里的 JS 没有自动化测试，但 markdown 渲染器（表格分隔行、按列上色、⚠ 标题）可以单独在 node 里跑：
把 `ui/index.html` 里的 `<script>` 抠出来，喂一份报告样本，检查生成的 HTML。
